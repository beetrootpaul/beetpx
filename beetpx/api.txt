package beetpx_bpx
	The main API, for controlling the game, exposing the building blocks, etc.

	Names prefixed with `p_` are a predefined set of colors based on some well
	known existing palettes. Names prefixed with `u_` are a set of tools and
	helpers.

		set_on_draw :: proc(on_draw: On_Draw) {...}
			Registers a callback to be run once per host frame, after any ticks.

			Do not assume `on_update` and `on_draw` alternate: between two `on_draw`
			calls, `on_update` may run several times, or not at all.

		set_on_update :: proc(on_update: On_Update) {...}
			Registers a callback to be run once per fixed-timestep tick.

			Do not assume `on_update` and `on_draw` alternate: between two `on_draw`
			calls, `on_update` may run several times, or not at all.

		start :: proc(canvas_size: Canvas_Size_Preset, tick_rate: Tick_Rate_Preset) {...}

		timer_has_finished :: proc(t: Timer) -> bool {...}
			Whether the timer has finished already.

		timer_make :: proc(ticks: u32) -> Timer {...}
			Makes a timer that finishes after a specific number of ticks.

			A negative `ticks` is treated as 0. `ticks` of 0 means a timer which has
			already finished.

		u_noop :: proc() {...}
			No operation. A helpef proc useful in situations where we want to pass

		u_ping_pong :: proc(t, range: int) -> int {...}
			Bounces back and forth between `0` and `range`.

			For a given `t`, it calculates the value that starts at `0` for `t=0` and
			goes up to `range` (or down, if `range` is negative), then back to `0`, and
			so on. For example, with `range` of 3, the results for `t=0..8` are
			`0,1,2,3,2,1,0,1,2`.

			TODO: Consider making it work for floats as well.
			TODO: Use `$T` to make it work for other types of integer numbers, so we
			      don't have to `int(…)` cast it on the caller side. Claude suggested
			      `intrinsics` to check for the type's type, but I see a `$T/Foo`
			      notation in the official demo: https://github.com/odin-lang/Odin/blob/master/examples/demo/demo.odin#L956-L957 .
			      Maybe we can leverage that?
			TODO: Should this proc be named like this and placed in `utils`? Think about
			      a bigger picture with ease, tween, lerp, clamp, waves (triangle, sine,
			      etc.). Also consider aligning with common industry practices (should we
			      operate on angles and turns)? Make sure procs are composable.

		u_round :: proc(values: [$N]f64) -> (rounded: [N]int) {...}
			Rounds an array with all elements rounded up.

			In contrary to built-in Odin's `math.round`, this proc rounds negative halves
			up towards 0, not the other way. This decision was made to achieve
			consistency in rounding of values across both negatives and positives.

	types
		Canvas_Size_Preset :: enum {Square_64, Square_128, Square_256}
			The size of the game drawing canvas, in logical pixels.

		On_Draw :: proc()
		On_Update :: proc()
		Rgb :: [3]u8
			An opaque RGB8 color.

		Tick_Rate_Preset :: enum {Hz_30, Hz_60}
			How many times per second `on_update` tries to run.

		Timer :: struct {_ticks: u32, _start_tick: u32}
			A timer implementation, tightly integrated with the game loop. It
			automatically counts ticks.

		Xy :: [2]f64
			Basic `(x,y)` coordinates type.

		Xy_Int :: [2]int
			Basic `(x,y)` coordinates type, as integers.

package beetpx_bpxd
	API for drawing things from inside `on_draw` proc.

	procedures
		clear_canvas :: proc(color: bpx.Rgb) {...}
			Sets every pixel of the canvas to a given color.

		rect_filled :: proc(xy: bpx.Xy, wh: bpx.Xy, color: bpx.Rgb) {...}
			Draws a filled rectangle of size `wh`, with one of its corners at `xy`.

			A negative width makes the rectangle extend from `xy` to the left, and
			a negative height makes it extend from `xy` to the top.

	proc_group
		pixel :: proc{_pixel_xy, _pixel_x_y}
			Draws a single pixel at `(x,y)`.
